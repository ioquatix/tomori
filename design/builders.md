# Builders

This describes how other projects build their own Tomori server and headset from Tomori's crates.

## Requirement

Another project builds a server of its own on the `tomori-server` library, without forking Tomori or changing its source: it registers backends and environments through the library's builder, `tomori_server::Server::builder()`, which starts with Tomori's own backends and no environments, since every environment, Tomori's own included, registers itself from its own crate (see `environments.md`). What it can register is what Tomori supports today:

- **Backends:** any implementation of `tomori-backend`'s `Backend`, from any crate, registered under the name `--backend` and clients name it by, which must be its `Backend::name`. The server treats it as it treats OpenCode's; nothing in the server names a concrete backend. Registering a name already registered replaces that backend.
- **Environments:** an identifier, a label, a protocol version, 1 unless given with `Environment::with_version`, each from the environment's common crate for one of its own crates, such as Sky's, and the environment's layer of a space's instructions (see `spaces.md`), offered to clients in the order registered, a later one with the same identifier in place of the earlier. The first offered is the default, as `environments.md` requires; a builder that registers none offers none, so that every space creation is refused. `Builder::environments` lists those registered. An environment may also bring a server side, which the server runs for each space bound to it, as `environments.md` requires; registering an environment again replaces its server side with the new one's, or removes it when the new one has none.
- **Configuration:** hooks that change the configured server before it serves, through its public settings; and command-line options of its own, `tomori_server::CommandOption`, added with `Builder::option`, such as an environment's configuration: `--help` lists each after Tomori's own options, in the synopsis and among the options, the command line reads its value, refusing one it cannot read, and it changes the configured server, after speech synthesis is configured and before the hooks run, in the order the options were added, the last value given of each. Adding a flag already added replaces that option in its place. The GitHub prototype's `--github-repository` is such an option, which its server crate adds.

Environments' client sides and state synchronization (#75, #76), data sources (#83) and tools (#82) will be registered through the same builder once Tomori has them; until then the builder offers nothing for them.

A server built this way takes the same command line as `tomori-server`, including `auth`, and serves the same way: admission, TLS, pairing, advertising, speech, kept spaces and shutdown follow `server.md`, `security.md` and `spaces.md` unchanged. `--help` lists the backends registered.

The `tomori-server` executable is Tomori's own program built on that builder, in a package of its own, `tomori-server-app` (`crates/server-app`), which depends on the library and on Sky's common crate: `tomori_server_app::builder()` registers, through the same calls another project's server makes, Sky, then the Minimal grid, labelled Grid, beside Tomori's own backends, `fake` and `opencode`, and `tomori-environment-github-server`'s `register` adds `--github-repository`, which offers the GitHub prototype after them when given a repository. A package of its own, rather than a feature of the library's, keeps the library free of every environment's crate whatever its features, so that an environment's server crate can build on the library without a cycle. Its command line, output and behaviour are those it had before; it is built with `cargo build -p tomori-server-app`, run with `cargo run -p tomori-server-app --bin tomori-server`, and installed with `cargo install tomori-server-app`, whose features are the library's.

An example downstream crate, `tomori-example-server` in `examples/server`, depends on the published crates as another project would, registers Sky and the grid, as Tomori's own server does, and a placeholder backend and environment through the builder, and is built and run by the workspace's tests.

Another project likewise builds a headset of its own on the `tomori-client-quest` library, whose library is `tomori`, through `tomori::Builder`, which starts with nothing but the built-in grid. What it can register is what Tomori supports today:

- **Sceneries:** what the headset draws for a space bound to an environment, by the environment's identifier and at the environment's protocol version: an implementation of `tomori-render`'s `Scenery`, drawn natively in each eye's pass as Sky is, made for the renderer's targets by a function it registers, with `Builder::scenery` at version 1 or `Builder::versioned_scenery` at another. Registering an identifier already registered replaces that scenery and its version. The grid, `minimal`, is built in, at its own version: a scenery registered for it is drawn with it, and the grid is still listed and compared at its own version, whatever version the scenery is registered at. The grid is also what a build shows, naming the environment and the version, for a space bound to one it has no scenery for or has at another version (see `environments.md`). Tomori's own build registers Sky from `tomori-environment-sky-client`, whose `register` registers its scenery at Sky's identity, and the farmyard from `tomori-environment-farmyard-client`, whose `register` registers its scenery and teleport profile at the farmyard's (see `farmyard.md`), with `Builder::register`, which hands a build's `Sceneries` to an environment's own registration. A build's `Hello` lists the grid, each environment it registers a scenery for, with its version, and each it presents over the grid, so that its server offers it only those.
- **Presentations over the grid:** an environment whose spaces a build presents with the grid and what the shared scene draws for it, without a scenery of its own, at the environment's version, with `Builder::present_over_grid` or `Sceneries::present_over_grid`, as Tomori's own build presents the GitHub prototype, whose cards the scene draws. Presenting an identifier again replaces its version; a scenery registered for the same identifier is drawn instead.
- **Locomotion:** the profile of an environment, by its identifier: none, the default, teleport onto walkable surfaces, or fly, as `locomotion.md` describes, declared with `Builder::locomotion` or `Sceneries::set_locomotion` and applied in a space bound to that environment when the build draws its scenery. Declaring an identifier again replaces its profile. Of Tomori's own environments, only the farmyard declares one, from its own crate, so Sky and the grid have no artificial travel. This is provisional: once environments have server sides (#180), the profile is to move to the environment's server side, so that everyone in a space has the same one.

A scenery, its version and its locomotion profile are all of an environment's client side that a headset build registers until state synchronization (#76) gives a client side more to present; an interface for client sides is introduced then, through the same builder.

`Builder::run_android` runs the headset on the Quest, from a build's own `android_main`: the `tomori` library's own, which runs Tomori's own build, `tomori::app::builder()`, is its default `app` feature, which a build of another project's turns off by depending on `tomori-client-quest` with `default-features = false`, so that its `android_main` is the only one, and so that it builds none of Tomori's own environments' crates it does not register. The `app` feature is Tomori's own app in the package that also builds the library, rather than a package of its own, because the APK is built from this package, with its library, `libtomori.so`, and its manifest; it is the only way a core crate depends on an environment's crate. `run_xr` runs it on a desktop OpenXR runtime; `run_desktop` and `run_demo` run the desktop windows, through a shell: `tomori::Desktop`, the window system, or a test's, which shows the same contents on the shared test device; and `run_console` the console, which names the build's environments. `tomori::main(builder)` is the `tomori` executable's command line, whose `--xr`, `--desktop`, `--console`, server-less window and spectator modes run the builder's, whose desktop window's **E** cycles through its sceneries, and whose `--help` names them for `TOMORI_ENVIRONMENT`. The `tomori` executable and APK are Tomori's own build, `tomori::app::builder()`, behind the `app` feature; their command line and behaviour are those they had before. The spectator draws the sceneries it is given: the `tomori` executable's spectator modes give it the build's, and the `tomori-spectator` executable gives it Tomori's own, `tomori_client_spectator::app::sceneries()`, behind that crate's default `app` feature, which `tomori-client-quest` turns off.

A headset build is packaged as an APK of its own without changing Tomori: its own application ID, APK name, label, launcher icon and assets, in a copy of `tomori-client-quest`'s `[package.metadata.android]`, which is the only one `cargo-apk` reads. `scripts/android.sh --package NAME` builds, installs and runs any such package, in the dev profile or, with `--release`, the release profile signed with a key it is given (`android-release.md` describes Tomori's own release APK), reading its application ID, APK name and OpenXR loader folder from its manifest, and `scripts/fetch-loader.sh` fetches the loader into the folder it names. The intent extras and the log tag are the framework's, the same for every build. `crates/client-quest/context/android.md` is the guide.

An example downstream crate, `tomori-example-headset` in `examples/headset`, registers Sky from its crate, as Tomori's own build does, and a placeholder floor for the example server's placeholder environment, and is built and tested by the workspace's tests. It is packaged as its own APK, `com.example.tomori.headset`, with its own label, icon and asset, on every pull request.

## Rationale

Other projects, such as a private integration with environments of its own, need their own server and headset with their own environments, data sources and tools, without forking Tomori or adding their specifics to its source (#73, and the environment framework proposal in #90). Registering backends and environments is what the server can support now; the rest of the framework slots into the same builder as it lands, rather than ahead of its design. The live server and the people who run `tomori-server` depend on its command line, so the default build must not change. Planned in #73 in November 2026. In November 2026 the maintainer agreed that the builders start empty and Tomori's own programs register Tomori's own environments as another project's would (see `environments.md`); the server's program moved into `tomori-server-app` so that GitHub's server half can build on the library, which a feature of the library's own could not without a cycle.

## Scope

The `tomori-server` library's builder and the registries it fills, the `tomori-server` executable in `crates/server-app`, and the example in `examples/server`; the headset's builder, `tomori-render`'s sceneries, the `tomori` executable and the `app` features of `tomori-client-quest` and `tomori-client-spectator`, Android packaging (`scripts/android.sh`, `scripts/fetch-loader.sh` and the manifests), and the example in `examples/headset`.

## Validation

- Test that a backend registered through the builder is offered by name, listed in `--help` after Tomori's, replaces one registered under the same name, and is refused when its own name differs from the one it was registered under or its constructor fails; and that a builder offers no environment until one is registered, and then those registered, in order, or a later one in place of an earlier with the same identifier, with their instructions and versions.
- Test against a fake backend that a registered environment's layer reaches the agent as its `tomori-environment` instruction entry, for a space created in it, changed to it or from it, and restored after a restart, including when a hook offers the environments after the kept spaces are listed again (see `environments.md`).
- Test that the example's executable lists its placeholder backend in `--help`, offers it and the placeholder environment in `Welcome`, and creates a space with both, whose state shows the environment's layer of the instructions.
- Test that Tomori's own server program offers Sky and then the grid, labelled Grid, at their crates' versions, and the GitHub prototype too when given a repository.
- Test that an option a builder adds is listed in `--help` after Tomori's own, needs its value, refuses one it cannot read, is applied with the last value given, can fail the server's start, and is replaced by one added later with the same flag.
- Compare `tomori-server --help`, an unknown argument, `auth --help` and a malformed `--github-repository` between a revision that changes the builder or the program's package and the one before it, and the startup output with the live server's flags, `--backend opencode --name NAME --speech-root PATH --speech-backend offline --workspace-root PATH` with token authentication and TLS, on a loopback port, without advertising and with an unreachable `--opencode-url`: they must be identical apart from ports, paths, fingerprints and times.
- Inspect the examples: each depends only on published crates and uses only their public interfaces.
- Test that the headset builder's default draws nothing but the grid, and Tomori's own build the grid, Sky and the farmyard, at version 1, with the farmyard's teleport profile alone, and presents the GitHub prototype over the grid; that a registered scenery is listed after them, with its version, or replaces one with the same identifier and its version, as does an environment presented over the grid; that a participant's `Hello` lists them; and that a conversation and renderer given its sceneries draw a space bound to its environment, where a build without it shows the grid and names it.
- Test that the headset builder's window modes, as `tomori`'s command line runs them through a test's shell, create a registered scenery and draw it once **E** or a space reaches its environment, and that its participant draws the build's environments; and check that each test fails when the builder, the command line or the window passes other sceneries instead, or leaves the build's environments out. Test that `--help` names the build's environments for `TOMORI_ENVIRONMENT`, and that the spectator lists and draws the sceneries it is given, and the grid alone until then.
- Test that the headset example draws its floor for a space in the placeholder environment on the shared test device, and in the server-less window that `tomori`'s command line opens for its build once **E** reaches it, and that its executable takes `tomori`'s command line.
- Link the headset example's library for Android at the Quest's API level: it exports one `android_main`, its own, and with the `tomori` library's `app` feature left on, linking fails with a duplicate `android_main`.
- Package the headset example with `scripts/android.sh --package tomori-example-headset build`, in CI, and check its APK with `aapt`: its application ID, label and icon are its own, its assets hold its own file and Tomori's licence notices, and it holds its own library and the OpenXR loader, not `libtomori.so`. `scripts/android.sh build` still produces `tomori.apk`, `com.codeotaku.tomori`.
- Run `cargo publish --workspace --dry-run --locked`.
